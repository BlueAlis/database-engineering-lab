Problem 1 — JOIN+DISTINCT vs IN vs EXISTS
Run against: public schema, real lab seed data (setup/schema.sql + setup/seed.sql)
Dataset size: customers=10, orders=20, order_items=30, products=12
Indexes present: primary keys only (no secondary indexes)
Postgres version: postgres:16 (container dbeng-lab-postgres)

from customers c
inner join orders o on c.id = o.customer_id

=== (c) EXISTS ===

select c."name", c.city
from customers c
where exists(
	select 1
	from orders o
	where o.status = 'completed'

=== Observation (raw, not yet a conclusion) ===

At this dataset size (10 customers / 20 orders), IN and EXISTS produce the
identical plan (Hash Semi Join, no separate dedup step). JOIN+DISTINCT adds
an extra Sort+Unique on top of the same Hash Join. Timing differences here
(0.7ms vs 0.05ms) are NOT statistically meaningful at this row count — see
the bench_02 run below for a size where the timing gap is backed by real
work rather than noise.
