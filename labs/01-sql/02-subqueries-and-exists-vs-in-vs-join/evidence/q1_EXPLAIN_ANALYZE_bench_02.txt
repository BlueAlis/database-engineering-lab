Problem 1 — JOIN+DISTINCT vs IN vs EXISTS
Run against: bench_02 schema (synthetic, scaled-up, isolated from the real
lab seed data in `public` — created for this experiment only, dropped
afterward, not part of the repo's tracked dataset).

Schema (subset of the real one, only what problem 1 needs):
  customers(id, name, city, customer_type) — PK only
  orders(id, customer_id FK, order_date, status) — PK only, no secondary index

Dataset size: customers=5,000, orders=150,000
  status breakdown: completed=90,147, cancelled=59,853
Generation: SERIAL id + generate_series, city/customer_type/status assigned
  via random(), order_date random within 2024. Not representative business
  data — sized only to make the DISTINCT-dedup cost non-trivial to measure.
Postgres version: postgres:16 (container dbeng-lab-postgres)

=== Observation (raw, not yet a conclusion) ===

At this scale the planner's strategy differs from the small-seed run: for
(b)/(c) it deduplicates orders.customer_id FIRST via HashAggregate
(90,147 rows -> 5,000 groups, narrow integer column), THEN hash-joins
against customers. For (a), it hash-joins FIRST (producing the full
90,147-row join against the wider name+city payload), THEN deduplicates
via HashAggregate on the wider result. That ordering — dedupe-before-widen
vs dedupe-after-widen — is the concrete reason (a) costs ~31ms vs ~18ms for
(b)/(c), not "DISTINCT is just slow" in the abstract.

At this row count (150K) the ~13ms gap is backed by real measured work
(Seq Scans reading 90K+ rows, HashAggregate over that many rows), unlike
the sub-millisecond seed-data run above where the gap was noise.

bench_02 schema was dropped after this run — not part of the tracked
dataset, not reproducible by re-running setup/seed.sql. If this needs to be
re-verified later, regenerate with the same generate_series approach
(5,000 customers / 150,000 orders, ~60% completed).
